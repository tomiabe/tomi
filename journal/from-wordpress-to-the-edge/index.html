From WordPress to the Edge

Why We Stopped Patching and Started Over

Somewhere around the fourth or fifth plugin update that broke the site, we stopped treating the problem as fixable.

Susinsight, our publication on sustainability and development in Africa, ran on WordPress. WordPress did what WordPress does. The site worked, stories were published, readers came, and then more readers came, more stories went up, more images filled the media library, and the system started signalling, quietly at first, that something was wrong. Pages loaded slowly, and the media library became clogged. Every CMS update introduced at least one new conflict somewhere else in the stack. We patched. The patch created a different problem. We patched that too.

This went on longer than it should have.

The real issue was not the platform itself. WordPress is adequate for most things. What we needed Susinsight to do had grown past what we were willing to build inside a WordPress environment. The content model required taxonomy across SDGs, World Days, regions, countries, and multiple content types. Author pages, Contributor profiles, Series archives, Regional pages, A glossary, etc. Building all of that inside WordPress meant custom post types, plugins, and a maintenance burden that kept expanding with no clear ceiling.

At some point, the cost of staying outweighed the cost of leaving.

We did not pick a new stack immediately. There was a period of writing down what the actual requirements were, not what we assumed they were. The content model came first: what is a Story on Susinsight, what is a Signal, how does a series function as a structure, and what does a reader need to navigate one. We had been running those content types informally for a while. The rebuild forced us to make them explicit.

Once the content model was clear, the stack followed: Next.js for the front end. Cloudflare Workers for deployment. A flat-file CMS (Pages CMS) that keeps content in markdown and JSON, version-controlled in GitHub, edited through a browser interface. Two people, one repository, one deployment pipeline.

Key terms in this rebuild
• Cloudflare Worker: a small program running on Cloudflare’s servers that serves our site to readers, instead of a traditional web server.
• Manifest file: a single file that lists all the pages and assets the Worker needs to serve.
• Repository: the codebase where all of the site’s files live, tracked in Git.
• Slug: a URL‑friendly version of a title, like “tomi-abe” instead of “Tomi Abe”.

The reader-facing changes were real. Load times improved. The content model became navigable: readers can browse by tags, SDG, region, World Day, story category, series, and author. That structure did not exist on the old site in any usable way.

What did not change is the editorial work. A story about solar-powered maternal health clinics in Tanzania takes the same amount of reporting and writing regardless of what CMS sits behind the publish button.

The first fully live version of the site had predictable problems. The manifest file that bundled all content for the Cloudflare Worker was saved directly into the codebase on GitHub, which meant changes in the CMS did not appear on the live site until someone manually regenerated and committed the file. We caught that in production. The fix was straightforward; the problem had been sitting there longer than we realized because there was no second pair of eyes in the deployment chain before the changes went live.

Some category and series pages also broke quietly for a few weeks. For example, the CMS saved “series” names as display text, “Critical Lifelines,” while the bit of code that decided which posts belonged in each series expected a slug — a URL‑friendly version like “critical-lifelines.” Posts were missing from their series pages. Again, not complicated to fix, but the gap between writing the code and seeing the problem on the live site was long enough to matter.

Both problems share a pattern: assumptions that held during development did not hold in production, and the team was small enough that the deployment chain had no built-in review step. That is the actual cost of building lean. Not the technical decisions, but the absence of the second person who would have caught what the first person missed.

That is the honest version of the first rebuild cycle. The next posts in this series will get into specific parts of the build: the CMS configuration, the content model decisions, the deployment pipeline, and what each of those looked like before we got them right.
